고친 것:
1. 한 줄에 단위가 여럿(`<K>`)이면 단위마다 제 조각에(예전: 줄 번호 사전이 앞 단위를 덮어씀 — 코덱스 지적 1).
2. 여러 줄 단위는 첫 조각에 전문, 나머지 조각은 비우고 글자만 있던 줄은 지움 7,786줄(예전: 뒷줄 일본어가 남음 — 코덱스 지적 2).
   단위↔조각 맞춤은 내용 글자(가나·한자·영숫자)로, 기호뿐인 조각은 단위 원문에 들어 있을 때만 묶는다.
3. 정렬 도구가 파일 경계(앞 파일 끝 줄 + 다음 파일 첫 줄)를 한 단위로 묶은 10곳은 `SPLIT` 표로 나눔(한국어는 나누기만).
4. **반각 기호**: 엔진(`s_dbRunningScript` 0x130AF8~, `dbGetStringMultiByte` 0x13B090)은 반각 중 공백·`!`·`?`·`' . _ +`·영숫자만 전각으로 바꿔 그린다.
   나머지(`, ~ - ( ) : % & = $` 등)는 글자 칸이 안 채워져 깨진다 → 빌드에서 전각으로(~ 838, - 221, ( ) 120 …). 낱자 ㄱ 1곳은 「기역」.
5. 역추출 대조(코덱스 지적 3): 다시 풀어서 모든 단위·조각이 제자리 한국어인지, 일본어가 남은 조각이 어디인지 전수.

## ★ 글꼴 수리 (11-01 03:1x, 사용자 캡처 「任장……어디냐!?」)
- 증상: 「젠」이 한자 「任」으로 나왔다. 전수 계산하니 **캐리어 2,361음절 중 732음절(31%)이 한자로 깨져** 있었다(가·개·게·기·그·국·길·다·계·속 …). 8월 v2 부터 있던 결함.
- 원인: 원본 글꼴 쪽(69쪽 전부)은 **0번 칸이 비어 있고 칸 번호 = JIS 점**이다. 엔진(dbInitFontSystem)은 쪽 시작 코드를 …3F/…9E 로 잡아
  칸 s4 = 점 그대로 읽는다(쪽마다 코드 목록 +0x2020, 그림 주소 +0x20E0, 표 간격 0x2260). 그런데 8월 `tools/repaint_font.py` 는
  칸 = (점−1) 로 그리고, 그 어긋남을 「엔진이 다음 글자를 그린다(+1)」로 오해해 inside.txt 의 **다음 한자** 칸에 그렸다.
  다음 한자가 JIS 바로 옆일 때만 맞고, 사이에 안 쓰는 한자가 끼면(任 다음 妊이 비어 있음) 캐리어 칸에 한자가 남았다.
- 고침: `release/repaint_font_v3.py` — 같은 캐리어 표로 각 한글을 **자기 캐리어 칸(칸 = 점)**에 그림 → `work/font_ko_v3`.
  검증: 캐리어 칸 2,361 전부 칠해짐 / 캐리어 아닌 칸 변화 0 / 예전에 맞던 1,629음절은 그림 바이트가 같음(그리는 방식 동일) /
  엔진 규칙(칸 = 점)으로 대사를 모사해 그리면 옛 글꼴은 캡처와 똑같이 「任장」, 새 글꼴은 「젠장」.
